Vectorizing loops at the IR1 level: why the second pass is off

State of things
---------------

src/compiler/vectorize.lisp holds two passes.  The source-form pass ships: it
rewrites a recognized DOTIMES/DO/LOOP form during IR1 conversion, before
macroexpansion, using the ctype of each variable's leaf.  tests/auto-vectorize*.lisp
and tests/auto-vectorize-differential.pure.lisp cover it.

The second pass, *VECTOR-NODE-SPLICE*, recognizes an elementwise loop on IR1 after
LOOP-ANALYZE and is off.  What it can do that the source pass cannot: see
arithmetic that only exists after inlining.  For

  (declaim (inline helper-add)) (defun helper-add (x y) (+ x y))
  (dotimes (i n) (setf (aref c i) (helper-add (aref a i) (aref b i))))

the source pass never sees a "+" -- at source level the body is still a call -- so
it declines; the IR1 pass sees the inlined load/load/add tree and vectorizes it.
tests/auto-vectorize.pure.lisp :IR1-VECTORIZES-AN-INLINED-CALL asserts both halves
of that, so it fails if either stops being true.

Why it cannot be enabled
------------------------

It recognizes the loop, prints a DOTIMES for the emitter to rewrite, and converts
that form in place, inside a live component.

IR1 registers an ENTRY node on (LEXENV-LAMBDA *LEXENV*) when it is created
(ir1-translators.lisp:199-208, 294-314), and everything else finds an entry's home
through (NODE-HOME-LAMBDA ...), which walks out of a :DELETED or :ZOMBIE lambda to
the caller (ir1util.lisp:1382-1389).  A LET merge or a LET-converted transform
between the two leaves an ENTRY that one lambda registered and another is asked
about.  In-place conversion creates exactly that situation, because inline
expansion and source transforms build their lambdas in the middle of an existing
component.

Symptoms, in the order they were found:

- a self-build with the pass on stops in MAKE-WEAK-VECTOR and later shapes with
  "#<SB-C::ENTRY ...> is not in ENTRIES for its home LAMBDA" (debug.lisp:517-519);
- the offending entry sits in LIVE code -- (block-delete-p) NIL, reachable from
  the component head -- so it is not debris from the deleted region;
- ENVIRONMENT-ANALYZE iterates LAMBDA-ENTRIES (envanal.lisp:277), so a detached
  entry loses its cleanup: an NLX target with a missing unwind.  This is the part
  that makes it a correctness problem and not a failed assertion.

*VECTOR-NODE-CHECK-ENTRIES* (off by default) asserts it at the splice, where the
component is still intact; it fires for the differential harness's simplest shapes,
which is the evidence that the problem is general to in-place conversion.

Deleting the loop's blocks
--------------------------

Two things are settled and should not be undone:

- do not call DELETE-BLOCK on the loop's own blocks.  DELETE-LAMBDA deliberately
  leaves a deleted lambda's blocks queued (ir1util.lisp:2191-2194), so hand
  deletion leaves ENTRY/EXIT bookkeeping inconsistent;
- do not call FIND-DFO inside the splice either.  The replacement's functionals sit
  in COMPONENT-NEW-FUNCTIONALS and are not reachable until LOCALL-ANALYZE-COMPONENT
  runs, so a sweep there can delete the replacement as unreachable.

unlink-blocks / link-blocks / (setf (component-reanalyze component) t), then let
LOCALL run and the next round's dfo-as-needed sweep the region transitively.

Options for finishing it
------------------------

1. Build the replacement as IR1 instead of converting a form.  Correct, and it is
   what the pipeline expects, but it means reimplementing
   VECTOR-ELEMENTWISE-PLAN / VECTOR-EMIT-ELEMENTWISE (the guards, the 256/128
   dispatch, the scalar tail, the alias check, and the WITH-ARRAY-DATA hoisting)
   as IR1 construction, i.e. writing the tested half of the feature a second time.

2. Convert the replacement into a FRESH LAMBDA and splice a call to it, passing
   the loop's arrays as arguments.  Conversion is then top-down into a new lambda,
   which is the shape IR1 expects, and LOCAL call analysis can inline it back.  The
   recogniser keeps its work; the risk moves to the splice: the call must be
   analysed before the loop's blocks go, and the arguments must be free of
   evaluation order surprises.  This looks like the cheapest sound route and has
   not been tried.

3. Share the emitter's VLOOP.  Build the (DEFSTRUCT VECTOR-LOOP) the source pass uses
   and call VECTOR-EXPAND-LOOP on it, converting the form that returns.  This
   deletes VECTOR-NODE-SOURCE-FORM and the second set of shape rules, and makes the
   one-element-type rule enforced rather than assumed (VLOOP has one element type,
   and the source pass requires the stores to agree).  It does NOT by itself fix
   the ENTRY problem, since it still converts a form in place -- it is worth doing
   before 1 or 2 because it shrinks what would have to be built.

Progress on option 2 (fresh lambda), and where it stops
-------------------------------------------------------

Implemented: the replacement is a LABELS local function called with the loop's
arrays and its limit, with the array types declared (a fresh lambda inherits none,
and the source pass reads types from declarations).  The differential harness still
reports 50 of 54 shapes packed with correct values, and the inlined-call shape is
still vectorized, so the wrapper costs nothing.

What it fixed: the self-build with the pass on no longer stops with "ENTRY is not
in ENTRIES for its home LAMBDA".  Converting into a lambda of its own gives IR1 the
top-down conversion it expects, which is what the note predicted.

Where it now stops: cross-compiling src/code/weak.lisp aborts with

  attempt to THROW to a tag that does not exist: SB-C::LOCALL-ALREADY-LET-CONVERTED

from RETURN-FROM (ir1-translators.lisp:231), which throws when the block's exit
ctran has been deleted.  Two forms were tried and both hit it: (FUNCALL (LAMBDA
...)) -- let-converted while being converted -- and LABELS.  The remaining
suspicion is the destination: the form is converted into the LOOP's exit ctran
(vector-node-splice-loop), which is a ctran the loop's own BLOCK/RETURN may already
have touched.  Converting into a fresh ctran chained before that block, or building
the lambda with IR1-CONVERT-LAMBDA and splicing a direct local call instead of
converting a LABELS form, are the two next things to try.

So option 2 is one step from working and one hurdle from working: the ENTRY problem
is gone, the new problem is a conversion-destination problem, in the splice rather
than in the emitted form.

Attempt 3, and the trap to avoid
--------------------------------

Catching the throw is not a way out.  Catching 'LOCALL-ALREADY-LET-CONVERTED around
the IR1-CONVERT of the replacement and declining leaves the component half
converted, and the next error is
  The value #<SB-C::LAMBDA-VAR ... :FLAGS (DELETED)> is not of type SB-C::CTRAN.
The throw must be prevented, not caught: the offending form has to be recognized
and refused before any conversion happens.

What the throw actually is, now that it has been read twice: GO throws when the
TAGBODY tag's ctran has been deleted (ir1-translators.lisp:335-336) and RETURN-FROM
when the BLOCK's exit ctran has (ir1-translators.lisp:231-232).  Both mean the
enclosing construct was let-converted out from under the code being converted.  A
LABELS body converted in place can hit this because the local function is
let-converted while its own body is still being converted -- SBCL only protects the
two places that expect it (locall.lisp:488, ir1tran-lambda.lisp:892).

Which leaves the option the note started with: build the lambda with
IR1-CONVERT-LAMBDA and splice a DIRECT LOCAL CALL, so no LABELS/FUNCALL form is
converted in a live component at all.  That is the next thing to try; everything
else in attempt 2 (declared parameters, fresh lambda, ENTRY bookkeeping) can stay.

Attempt 4: the emission form is not the cause
---------------------------------------------

Three emission variants were tried and all three hit the same throw in
src/code/weak.lisp:

  (LABELS ((f (arrays limit) (declare types) (dotimes ...))) (f ...))
  (FUNCALL (LAMBDA (arrays limit) (declare types) (dotimes ...)) ...)
  (LET ((f (LAMBDA ...))) (FUNCALL f ...))

and in all three the differential harness still packs 50 of 54 shapes with correct
values and the inlined-call shape still vectorizes, so the wrapper is not costing
anything else.  The throw therefore does not come from the block/tagbody of the
form we emit, which was the working hypothesis.

Next diagnostic, and it is the only one left that cannot corrupt the component:
print at the two THROW sites instead of catching it.  In
ir1-translators.lisp, before (throw 'locall-already-let-converted ...) at :231
(RETURN-FROM, the block's deleted exit ctran) and :335 (GO, the tagbody's deleted
tag ctran), print the ctran, its block number, whether that block is in
COMPONENT-DELETE-BLOCKS, and the ctran's next/prev node.  Then a self-build with the
pass on names the construct without leaving a half-converted component behind, and
with the form we emit already excluded, the answer is about the loop that is being
replaced rather than about its replacement.

A thought worth testing at the same time: the loop being spliced in MAKE-WEAK-VECTOR
is (dotimes (i length) (setf (weak-vector-ref v i) (elt initial-contents i))) --
WEAK-VECTOR-REF and ELT are both inline/transform expanded, so the nodes the
recogniser sees come from a transform, and a transform's lambda is exactly the kind
of functional that LET conversion can retire while other code still refers to its
tags.  If that is the mechanism, the pass must refuse any loop whose body contains a
node produced by a source transform (which the accounting check could identify: the
no-lvar :LOCAL call whose callee is bound inside the region).

Attempt 5: the throw site, found by instrumenting and getting nothing
--------------------------------------------------------------------

Prints added at the two THROW sites in ir1-translators.lisp (RETURN-FROM :231, GO
:335) produced no output while the weak.lisp compile still aborted, so the throw
comes from one of the other throwers.  It is IR1-CONVERT-LOCAL-COMBINATION
(ir1tran.lisp:1255-1257): converting a call to a function that has ALREADY been
let-converted throws, unless the function has an inline expansion to fall back on.

That explains all four emission variants at once.  LABELS, (FUNCALL (LAMBDA ...)),
and a LET-bound lambda all emit a CALL TO A LOCAL FUNCTION, and SBCL let-converts a
local function eagerly when it is called with suitable policy, so by the time the
call is converted the functional is :LET and the throw is unconditional.

So: a wrapper is the wrong shape.  The options left are

  (a) the bare DOTIMES (what the pass emits now) and repair the ENTRY bookkeeping
      afterwards.  A first attempt at that -- walking the new block and doing
      (PUSHNEW entry (LAMBDA-ENTRIES (NODE-HOME-LAMBDA entry))) -- aborted the
      weak.lisp compile with "The value NIL is not of type SB-C::CTRAN", so the walk
      over the freshly converted block needs care: the block's ctran chain is not
      in the state DO-NODES expects until the conversion's block is linked.
  (b) IR1-CONVERT-LAMBDA plus a call node built by hand (not converted from a form),
      and only after the functional is known not to be let-converted.  This avoids
      the form-conversion path entirely but has to build the combination and its
      arguments itself.

Option (a) is closer: the ENTRY repair is a few lines once the walk is right, and it
is the same fix-up MERGE-LETS performs (locall.lisp:1130-1140).

Attempt 6: the bare DOTIMES with an ENTRY repair, and the NEXT error to chase
------------------------------------------------------------------------------

Dropped the wrapper (attempt 5 explains why) and repaired the ENTRY bookkeeping
after LOCALL-ANALYZE-COMPONENT instead: walk the component's live blocks and
PUSHNEW every ENTRY onto (LAMBDA-ENTRIES (NODE-HOME-LAMBDA entry)), which is the
nconc MERGE-LETS already does for the same reason.

That aborts the weak.lisp compile with a different error:

  The value NIL is not of type SB-C::CTRAN

so the repair is not the only thing to fix: something in the splice path itself
reaches a NIL ctran for that loop.  Candidates, in the order worth checking:

- UNLINK-BLOCKS/LINK-BLOCKS when the loop's exit block has been merged, so the
  successor's ctran is nil;
- the conversion delivering into an exit ctran that is no longer the block's start
  ctran after a merge;
- the loop's blocks not being contiguous in the block chain at that point.

The way to find it without a build: take a core built with the switch OFF, set
SB-C::*VECTOR-NODE-SPLICE* at run time, and compile a lambda with the shape from
MAKE-WEAK-VECTOR (two DOTIMES in the two branches of an IF, inside a LET that binds
the destination).  That reproduces in seconds instead of two minutes and gives a
backtrace.

Option 1 in detail: what building the replacement as IR1 means
---------------------------------------------------------------

Everything the source pass does after recognition is in VECTOR-EXPAND-ELEMENTWISE-LOOP
(vectorize.lisp): guards, the 256/128 dispatch, the scalar tail, the alias check, and the
non-simple-array hoisting.  Option 1 does not reimplement that logic; it emits the SAME
constructs as IR1 nodes instead of as forms, so the logic stays where it is and only the
materialiser changes.

Order of work, smallest first:

1. Read VECTOR-EMIT-ELEMENTWISE and list the forms it produces: a LET that binds the data
   vectors and the count, an IF on the guard, the packed LOOP, and the scalar tail LOOP.
   Each of those has a direct IR1 analogue, and the template to copy is
   INSERT-CLEANUP-CODE (ir1util.lisp), which builds blocks and nodes in the middle of a
   component and is the one place in SBCL that does this on purpose.

2. Build the block chain first, with no nodes: preheader -> guard block -> {wide, narrow,
   tail, done}.  MAKE-CTRAN, CTRAN-STARTS-BLOCK, LINK-BLOCKS and UNLINK-BLOCKS are all
   available; the parts that bit us are that BLOCK-START must not be left nil on a block
   that something will join to (JOIN-SUCCESSOR-IF-POSSIBLE dies on it, ir1opt.lisp:519 ->
   ir1util.lisp:1897), and that deleting the loop's blocks must go through the DFO sweep,
   not DELETE-BLOCK.

3. Fill the packed loop body with VOPs, not forms: a VOP node per primitive the emitter
   would have called (%VEC-LOAD-*, %VEC-ADD-*, %VEC-STORE-*, the splat, the ramp).  This is
   the part that is genuinely new work and the part most likely to be wrong, because the
   primitive table's TYPE the emitter handles (SIMD-PACK types, the 128/256 split) has to
   be threaded through by hand.

4. The scalar tail can stay a form: it is plain scalar code with no vector constructs, so
   converting it with IR1-CONVERT into its own block is safe and is what the pass does
   today for the whole loop.

5. The guard needs the array bounds and the count, which are LVARs the recogniser already
   has; the alias check needs the arrays' leaves.

Two cheaper things worth doing BEFORE step 3, because they shrink it:

- option 3 (share the VLOOP): build the (DEFSTRUCT VECTOR-LOOP) the source pass uses and
  read the element type, index, count, stores and expressions out of it instead of the
  plan plist.  That deletes VECTOR-NODE-SOURCE-FORM and the second set of shape rules.
- keep a form-based fallback: build the skeleton in IR1 (steps 1, 2, 4, 5) and convert the
  packed body as a form into its block.  That gets the structural fix -- no conversion in
  the live component's own flow -- without writing step 3 at all, and it is worth trying
  first precisely because every failure so far has been structural, not arithmetic.

That last option is the one this session's evidence points at: convert the *packed body*
into a block of its own, constructed by hand, rather than converting the whole replacement
into the loop's place.  If it works it is option 1's benefit for a fraction of its cost.

Attempt 7: the plan was the blocker, not the splice
---------------------------------------------------

The brief for this attempt was the cheap version of option 1: build the block
skeleton by hand (guard, packed body, scalar tail, done) and convert only the
pieces as forms, so that nothing is converted into the loop's own place.  The
work started by measuring what the splice actually does wrong, and it does
nothing wrong.  What follows is the measurement, because it overturns the premise
every earlier attempt was working from.

*The entry check was broken, and it is the only reason anybody believed the ENTRY
problem was real.*  CHECK-ENTRIES-AFTER-SPLICE walked the component from
(COMPONENT-HEAD COMPONENT), and the head and tail blocks have no start ctran, so
DO-NODES begins with (CTRAN-NEXT NIL) and signals "The value NIL is not of type
SB-C::CTRAN".  That is attempt 6's error, word for word: it was the diagnostic
failing, not the splice.  Fixed (skip a block with no BLOCK-START), the checker
reports zero mismatches over the 54 shapes of
tests/auto-vectorize-differential.pure.lisp, with the splice on.  The ENTRY
bookkeeping of the in-place splice is fine as it stands: registration
(LEXENV-LAMBDA *LEXENV*) and home (NODE-HOME-LAMBDA) both come from the anchor's
lexenv, and MERGE-LETS maintains both together.  So option 1 in full -- build the
replacement as IR1 with VOP nodes -- is not needed for correctness.  The cheap
version is not needed either, and the block-building it asks for is what the
splice already does: VECTOR-NODE-SPLICE-LOOP makes a ctran, starts a block with
CTRAN-STARTS-BLOCK, converts into it, and delivers into EXIT's start ctran, which
is WRAP-PREDICATE's pattern (ir1tran.lisp:1200-1221).  No node is ever converted
into the middle of a live block.

*The wrapper was the LOCALL-ALREADY-LET-CONVERTED throw.*  Removed: the emitted
form is the bare DOTIMES, with the array element types carried as THE casts
instead of declarations on a wrapper's parameters (the casts are what the source
pass reads the types from, and what keeps a store's element type right when the
enclosing scope declares nothing).  The throw was not unconditional, as attempt 5
concluded; it needed the second splice a component can do, which is why the
harness never hit it and MAKE-WEAK-VECTOR did.

*The plan accepted a loop no backend can vectorize.*  The first thing a switch-on
self-build spliced was two loops in MAKE-WEAK-VECTOR over (SETF (SVREF V I) ...):
SIMPLE-VECTOR's element type is T, and VECTOR-NODE-PLAN took the element type
from the first store without asking whether the backend publishes a lane for it.
So it printed a DOTIMES that the source pass then declined to rewrite -- having
replaced a loop with itself.  The plan now refuses an element type with no LOAD
and STORE primitive, and refuses stores that disagree, since the emitter reads
one element type for the whole loop (VLOOP has one).

Where a switch-on self-build now stops
--------------------------------------

With those three fixed, a switch-on build compiles every file in make-host-2 --
it gets past src/code/weak.lisp and out the other side -- and then dies in warm
init, in the target's compilation of src/code/room.lisp:

  Perfect hash generator failed on #(:DYNAMIC :TEXT :FIXED :READ-ONLY :STATIC)

when compiling room.lisp, i.e. COMPILE-PERFECT-HASH's own validation
(early-c.lisp:135-170) rejecting a hash it just built.  That is target code
compiled by a host compiler that the pass corrupted, and the pass had *spliced
nothing* at that point.

Bisection, each step a switch-on self-build of make-host-1 + make-host-2 followed
by one warm-init compile of the cold core:

  splice off (HEAD)                            build green
  splice on, analysis and plan in the pass     dies as above, 0 splices reported
  splice on, FIND-DFO/FIND-DOMINATORS/LOOP-ANALYZE
             in the pass, no plan walk           build green
  splice on, FIND-DOMINATORS only              build green
  splice on, LOOP-ANALYZE only                 build green
  splice on, analysis + walk, no VECTOR-NODE-PLAN
                                               build green
  splice on, analysis + walk + VECTOR-NODE-PLAN
                                               dies as above, 0 splices reported

So it is the *plan* walk: calling VECTOR-NODE-PLAN on every natural loop of every
component in the cross-compiler corrupts the code that compiler generates, and
never splices anything, because during make-host-2 the backend has not published
its primitives and every plan refuses at the last check.

What was ruled out on the way, so it is not re-derived:

- FIND-DFO from the pass: it clears COMPONENT-REANALYZE and deletes every block
  it cannot reach, including the BIND block of a functional still queued on
  COMPONENT-NEW-FUNCTIONALS.  That is a real hazard, and the pass now declines
  while COMPONENT-REANALYZE is set.  It is not this failure.
- FIND-DOMINATORS leaving a stale dominator tree behind: SET-SLOT-OLD-P asks
  DOMINATES-P a semantic question with it (whether a slot store can skip its GC
  barrier, ir1util.lisp:1064-1073 and 1127-1133), which looks like a way to
  corrupt a heap.  Saving and restoring every BLOCK-DOMINATOR around the analysis
  changes nothing.
- the loop structure LOOP-ANALYZE leaves going stale: what reads it is heuristic
  (branch probabilities control.lisp:113, TN ordering pack.lisp:865, loop
  alignment ir2tran.lisp:2529).

Where the next person should look
---------------------------------

Inside VECTOR-NODE-PLAN, in this order, because everything before it is a plain
structure read:

1. LVAR-TYPE and the TYPE-SPECIFIER calls built on it (vector-node-tree, the
   store's element type, vector-probe-type).  LVAR-TYPE caches into
   LVAR-%DERIVED-TYPE (ir1opt.lisp:176-202), so a plan that runs between
   optimization rounds asks for and stores derived types at a moment the
   pipeline did not intend.  Try replacing every LVAR-TYPE in the reader with
   (SINGLE-VALUE-TYPE (%LVAR-DERIVED-TYPE ...)) -- which does not cache -- and
   see whether the self-build survives.
2. FLUSHABLE-COMBINATION-P (ir1util.lisp:1518-1533), which calls a per-function
   FLUSHABLE-TEST with the call for a node that is still live.
3. VECTOR-PROBE-NODE in the refusal messages: it formats and type-specifies every
   node it cannot account for, on every natural loop.

A cheaper way to sidestep all of it: recognise loops without the analysis.  The
pass needs, per candidate loop, the head block, the blocks of the natural loop and
the exit; those can be found by walking predecessors from a retreating edge, with
dominators in a private table instead of BLOCK-DOMINATOR, and nothing written back
into the component.  That deletes FIND-DOMINATORS and LOOP-ANALYZE from the pass
as well, and with them the two hazards above.

What is in the tree now
-----------------------

*VECTOR-NODE-SPLICE* is still NIL.  The source-form pass is untouched by this
attempt.  tests/auto-vectorize.pure.lisp (87 tests) and
tests/auto-vectorize-differential.pure.lisp are green, and with the switch on at
run time the differential harness still measures 50 of 54 shapes packed through
the IR1 pass alone, values passing, and the inlined-call shape vectorizing.

Attempt 8: private loop discovery, and what the warm-init failure really is
--------------------------------------------------------------------------

Attempt 7 recommended finding the loops privately instead of through FIND-DOMINATORS
and LOOP-ANALYZE, on the theory that the pass was disturbing state the pipeline
owns.  That is now done: VECTOR-NODE-FIND-LOOPS walks BLOCK-PRED back from every
retreating edge (BLOCK-NUMBER is reverse DFO, so a retreating edge goes from a
smaller number to a larger one -- the test LOOP-ANALYZE applies), which needs no
dominator tree at all, and the result is a pass-private (DEFSTRUCT VECTOR-NODE-LOOP)
holding the head, the blocks and the loops nested inside it.  Nothing is written
into the component, so the two hazards attempt 7 listed -- DFO-AS-NEEDED inside
FIND-DOMINATORS sweeping blocks a pending functional still owns, and a stale
BLOCK-DOMINATOR tree feeding SET-SLOT-OLD-P -- are gone rather than avoided.

It did not fix the warm-init failure, and the failure is not what it looked like.
Here is the ladder that says so.  Each rung is make-host-1 + make-host-2 followed
by one warm-load compile of the resulting cold core, which is ~40 s:

  switch off in the source, full pass compiled in        warm load passes
  switch on,  full pass                                  FAILS, 0 splices
  switch on,  full pass, pass disabled at RUN time
              (symbol-function of VECTOR-NODE-COMPONENT-PASS
               replaced before the warm load)             FAILS
  switch on,  pass body replaced at COMPILE time by
              (declare (ignore component)) nil            passes
  switch on,  full pass + *VECTOR-PRIMITIVES* gate so it
              never runs in the cross-compiler            FAILS
  switch on,  a comment changed and nothing else         FAILS

plus, from host-2 with *VECTOR-NODE-CHECK-PURITY* on:

  the plan ran 1761 times, spliced 0 times, and changed NOTHING in the component
  it planned: every BLOCK-REOPTIMIZE, BLOCK-FLUSH-P, BLOCK-TYPE-CHECK,
  NODE-REOPTIMIZE, LVAR-REOPTIMIZE and LVAR-%DERIVED-TYPE it snapshotted before
  the plan was identical after it.  (That checker is in the tree, off, as
  *VECTOR-NODE-CHECK-PURITY* -- it is the tool that produced this.)

Read together: the pass does not corrupt a component, does not splice anything
during a self-build, and its behaviour at run time in the failing warm load is
irrelevant (disabling it there does not help).  What makes the difference is the
pass being *compiled in* while the switch reads true -- remove either and the build
passes.  In other words the warm-init failure is not caused by what the pass does;
it is a latent layout-sensitive failure in the target's compile-time perfect-hash
path that the presence of this code perturbs.  An earlier attempt 7 bisection that
"proved" the plan walk was at fault was measuring that coin: the configurations it
compared differed in how much code they compiled, not in what ran.

Two things support the layout reading and are worth following up:

  - the only target fasl that differs between a switch-on and a switch-off
    make-host-2 is src/compiler/perfect-hash.lisp, and every function in it
    disassembles identically in both.  The difference is not code.  (Take the
    comparison with a pinch of salt: a controlled rerun, with the two sources
    differing only in the DEFVAR's value, is what to redo; the first comparison
    was confounded by other edits in the same file.)
  - pre-allocating a large array in a passing cold core before the warm load does
    not flip it, so it is not a plain heap shift.

Where to look next, in order:

1. Reproduce the failure in isolation, in the cold core itself, before it is
   overwritten: run the 5-key path at the debugger prompt of a failing build
   (SB-C::MINPERFHASH-KEY-UNIVERSE-TYPE, PREHASH-FUNCTION-FOR-MPH-GENERATOR,
   MAKE-PERFECT-HASH-LAMBDA, then SB-C::COMPILE-PERFECT-HASH on
   '(:DYNAMIC :TEXT :FIXED :READ-ONLY :STATIC)) and print the hashes and the
   generated lambda.  In a healthy build that path validates; the difference
   between the two must be the actual bug.
2. COMPILE-PERFECT-HASH validates by (EVAL LAMBDA) under *EVALUATOR-MODE*
   :INTERPRET (early-c.lisp:135-170), i.e. sb-fasteval compiles a lambda whose
   body is SB-C::UINT32-MODULARLY, which has a compiler macro
   (OPTIMIZE-FOR-CALC-PHASH, sxhash.lisp:322-325).  A validating interpreter that
   can answer differently because of where its code was loaded is a bug in that
   path, not in the vectorizer.
3. To get the gate itself green while that is sorted out: keep the pass out of the
   cross-compiler's *compiled image* -- a build with the pass body compiled in and
   the switch true is the failing combination.  Moving the pass to its own file
   that build-order places after perfect-hash.lisp, or putting the whole file
   behind a feature that make-host-1 does not define, would do it, and both are
   cheap.  That is a workaround, not a fix, and it should be labelled as one.

What is in the tree
-------------------

*VECTOR-NODE-SPLICE* is NIL.  Private loop discovery, the *VECTOR-PRIMITIVES*

Attempt 9: the pass was splicing during cross-compilation, and that is the whole failure
--------------------------------------------------------------------------------------

Attempt 8 concluded that the pass "splices nothing during a self-build" and looked for
a layout-sensitive bug in the perfect-hash path.  Both halves of that were wrong, and a
SERIAL make-host-2 says so in one line:

  ; file: src/compiler/perfect-hash.lisp
  ; in: DEFUN PHASH-HEXEIGHT
  ;     (SB-C::TRY (LOGAND SB-C::V 7) "(& val 7)")
  ; --> PROGN DOTIMES DO BLOCK LET
  ; note: vectorized loop over (UNSIGNED-BYTE 32), 8 elements at a time where the
  ;       machine has avx2 and 4 where it does not

The pass DOES run in the cross-compiler, and it does splice there.  Attempt 8's
measurement said otherwise because it counted splices with *VECTOR-NODE-TRACE* through
the parallel driver, which drops a subprocess's output, and because the primitives test
it added does not mean what it says: make-host-2 loads every HOST fasl up front
(`load-or-cload-xcompiler`), so src/compiler/x86-64/vec.lisp and vec-256.lisp have
published their tables before the first TARGET file is compiled.  (The source pass has
always been live there for the same reason; that is why the note above is a normal
build note and not a switch-on one.)

Why that breaks the build: the source pass rewrites the DOTIMES this pass prints, and
emits its wide/narrow dispatch as

  (IF (SB-VM::AVX2-AVAILABLE-P) <wide> <narrow>)

a direct call, compiled into a target file.  src/code/x86-64-vm.lisp is what proclaims
AVX2-AVAILABLE-P INLINE, and it is build-order 515 -- long after src/compiler/
perfect-hash.lisp at 165.  make-host-2 treats a warning as fatal:

  ; caught WARNING: Proclaiming SB-VM::AVX2-AVAILABLE-P to be INLINE, but 1 call to it
  ;   was previously compiled
  FAILURE-P was set when creating "obj/from-xc/src/code/x86-64-vm.lisp-obj"

and from there the corpse is unrecognisable: output/tls-init.lisp-expr is never written,
so the next genesis complains that the header files do not match, or warm init fails in
an unrelated file.  Attempts 7 and 8 chased those corpses.

The fix: the pass never runs in the cross-compiler.

  (defvar *vector-node-cross-compiling* #+sb-xc-host t #-sb-xc-host nil)

A cross-compiled target file that this pass vectorizes is a build-time optimization of
the compiler's own code, not of the program being built -- not worth an ordering
invariant that the emitted dispatch cannot keep.  With the test in place, a switch-on
self-build completes, serially and in parallel.

The bug the test suite then found, which is the real one
--------------------------------------------------------

Turning the switch on for the first time put 87 tests through a core that has the pass
on, and four failed.  Three are shape assertions of the source pass (see below); the
fourth was a genuine miscompile of the pass:

  (defun vectorize-u32-to-single (in out n)
    (declare (type (simple-array (unsigned-byte 32) (*)) in)
             (type (simple-array single-float (*)) out) ...)
    (dotimes (i n) (setf (aref out i) (* 2.0 (aref in i)))))

SBCL's transforms turn the multiply into (+ X X), with X bound by a LET inside the loop.
VECTOR-NODE-TREE read that leaf as a loop-invariant scalar and the splice printed

  (DOTIMES (#:VN-I N)
    (SETF (AREF (THE (SIMPLE-ARRAY SINGLE-FLOAT (*)) OUT) #:VN-I) (+ SB-C::X SB-C::X)))

replacing the loop -- and with it the binding of X -- with a loop that reads an
undefined variable.  The compiled code had a TLS reference to SB-C::X and the compiler
said "undefined variable: SB-C::X".  VECTOR-NODE-LOOP-INVARIANT-P now refuses a leaf
whose home lambda is bound inside the loop's blocks, which is the property that makes a
leaf survivable across the splice.

The three shape tests (:vectorize-loop-not-recognized, :vectorize-do-loop,
:vectorize-index-affine) assert that the SOURCE pass leaves certain shapes scalar: a DO
with a result form, a LOOP with a FINALLY, an integer index store.  The IR1 pass takes
all three, correctly, so those shapes are now recompiled through the source pass alone
(VECTORIZE-SOURCE-PASS-ONLY) before their disassembly is checked; their value checks run
on the file's own definitions either way.

Where this rests, and what is left for upstream
------------------------------------------------

The feature is two files and one hook.

  src/compiler/vectorize.lisp      the source-form pass: the vloop, the matchers, the
                                   emitter, and the primitive table a backend fills in
                                   (*VECTOR-PRIMITIVES*, *VECTOR-PRIMITIVES-256*).  On
                                   by default, *AUTO-VECTORIZE* turns it off.

  src/compiler/vectorize-ir1.lisp  the IR1 pass, build-order 388 -- after ir1util,
                                   locall, ir1opt, loop and dfo, which it reads, and
                                   before ir1final.  Placing it there is what let the
                                   two forward-reference ftype declaims
                                   (FLUSHABLE-COMBINATION-P, %LVAR-DERIVED-TYPE) go
                                   away.  It takes exactly one thing from the file
                                   beside it: VECTOR-PRIMITIVE.  On by default,
                                   *VECTOR-NODE-SPLICE* turns it off, and
                                   *VECTOR-NODE-CROSS-COMPILING* keeps it out of the
                                   cross-compiler.

  src/compiler/main.lisp           IR1-PHASES calls VECTOR-NODE-COMPONENT-PASS as a
                                   sibling of IR1-OPTIMIZE-PHASE-1, inside the
                                   fixpoint and inside the dynamic binding of
                                   *CONSTRAINT-UNIVERSE*.  It is a sibling rather
                                   than a step inside the optimize phase because a
                                   splice needs the round after it -- LET conversion,
                                   optimization, and the DFO sweep that retires the
                                   old blocks -- and because re-entering IR1-PHASES
                                   from inside it would build a fresh universe under
                                   lvars that index the old one.

Everything else that grew here while the pass was being made to work is gone: the
loop probe, the entry checker, the purity checker, the splice trace, and the special
variable that carried the loop's blocks into the planner (it is an argument now).  The
refusal keywords VECTOR-NODE-PLAN returns stay: they are the function's answer, and
they are what a compiler note would be built from if this ever needed one.

What is left for upstream:

1. History.  This branch is a stack of commits whose messages are a lab notebook
   (attempts 2 through 9 of the note).  Upstream wants one commit that adds
   src/compiler/vectorize-ir1.lisp, one that hooks it into IR1-PHASES, and NEWSCAST
   entries for the two switches; the note can be dropped to a short file or folded
   into the manual's "Automatic Vectorization" node.
2. Share the emitter (option 3 of the note, never done).  The IR1 pass carries a
   second set of shape rules and prints them as a DOTIMES for the source pass to
   rewrite.  Building the source pass's VLOOP instead and calling VECTOR-EXPAND-LOOP
   on it would delete VECTOR-NODE-SOURCE-FORM, make the one-element-type rule
   structural rather than checked, and drop the 50-of-54 coverage question: the IR1
   pass would then emit what the source pass emits, for the same shapes it can
   already recognize.  What it does NOT need is the rest of option 1 -- building the
   guard, the packed loop and the tail as IR1 nodes and the VOPs by hand -- because
   the splice turned out to be sound (attempt 7) and the emitter belongs in one place.
3. The 256-bit dispatch is what broke the first switch-on build (attempt 9): the
   emitted (IF (SB-VM::AVX2-AVAILABLE-P) ...) is a direct call, and a file that
   vectorizes before src/code/x86-64-vm.lisp proclaims that symbol INLINE aborts the
   build under make-host-2's fail-on-warnings.  The gate on *VECTOR-NODE-CROSS-COMPILING*
   is right for this pass, but the same trap is waiting for anything else that
   vectorizes compiler code during a build.

Rungs: making the pass build IR1 instead of printing source
-----------------------------------------------------------

The pass recognized at IR1 and emitted at the source layer -- it printed a DOTIMES and
let the source-form pass rewrite it.  No other optimizer in SBCL reaches back into
IR1-CONVERT from inside the optimizer, and the plan is to take that away in rungs so
that each one is reviewable on its own:

  A. structure: guard block + the loop kept as the scalar tail, packed body still a
     converted form.  Behaviour and numbers identical.
  B. the packed body as IR1 + VOP nodes, for one element type and one operator
     (single-float +), every other shape refused meanwhile.
  C. widen to the rest of the table (double-float, integer lanes, the 128/256 split,
     the ramp), one family at a time.
  D. delete VECTOR-NODE-PACKED-FORM and any remaining printed source, and move the
     pass into IR1-OPTIMIZE-UNTIL-DONE if it no longer needs a following round.

Rung A is landed.  The pass no longer replaces anything: it inserts a guard block on
the edge into the loop, and hangs the packed prefix off the guard's true edge; the
loop the pass found stays where it was and becomes the scalar tail, entered with its
own index variable already set to the first element the packed loop did not do.  The
printed form is now

  (WHEN <guard>  (PROGN (SETQ <loop's index> (- <count> (MOD <count> <width>)))
                        (DOTIMES (<k> <index>) <the stores at k>)))

where the guard is (AND (TYPEP <count> 'INDEX) (>= (LENGTH <array>) <count>) ...) for
every array the plan touches.  That is the source-form emitter's own shape -- guard,
packed loop, scalar tail -- with the original loop as the tail.

What rung A removed, and why it stays removed:

- the requirement that the loop have one way in AND one way out, and the delivery
  into the loop's exit ctran;
- UNLINK-BLOCKS on the loop's entry and the LINK-BLOCKS that replaced it;
- the whole class of problems that came from deleting blocks: the ENTRY repair, the
  DFO sweep timing, the "do not call DELETE-BLOCK here" rules.  The insertion uses
  CHANGE-BLOCK-SUCCESSOR, exactly as INSERT-CLEANUP-CODE does (ir1util.lisp:36-55),
  so an IF between the preheader and the loop is repointed for free;
- the dependency on the loop's exit block existing at all.

What it did not remove: the weak table.  The pass still has to stop itself after one
insertion per component, because the loop it leaves behind is the same loop it would
find again next round.

Numbers after rung A, unchanged from before it: 87 of 87 tests,
auto-vectorize-differential 1 of 1, the differential harness 54 of 54 packed through
both passes and 50 of 54 through the IR1 pass alone, values passing in both, and a
serial switch-on self-build completing.
